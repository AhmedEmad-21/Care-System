
# ⭐ Reviews System Integration Guide (`REVIEWS_GUIDE.md`)

> **إلى فريق الفلاتر:** يوضح هذا المستند الآلية الكاملة لنظام التقييمات، سواء تم تفعيل التقييم تلقائياً عبر الإشعارات أو يدوياً من ملف مزود الخدمة، مع تفاصيل الـ Endpoints والبيانات المتوقعة.

---

## 1. نظرة عامة على فكرة العمل (How It Works)

* يسمح النظام للمريض بترك تقييم (من 1 إلى 5 نجوم وتعليق نصي اختياري) لكل **زيارة مكتملة حقيقية (`completed`)** قام بها مع أي طبيب أو ممرض.


* كل حجز مكتمل يمنح المريض حق تقييم واحد مستقل؛ بمعنى لو أن المريض أجرى 3 زيارات مكتملة مع نفس الطبيب، سيكون متاحاً له تقييم الدكتور 3 مرات منفصلة (لكل زيارة تقييمها الخاص).

---

## 2. الطريقتان المتاحتان للتقييم (The Two Review Flows)

### الطريقة الأولى: التقييم التلقائي عبر الإشعار (Notification-Driven Review)

1. **ما يحدث في الباك إند:** بمجرد قيام الستاف بتحديث حالة الحجز إلى `completed`، يرسل النظام تلقائياً Push Notification للمريض.


2. **بيانات الإشعار المستقبلة في تطبيق الفلاتر (Payload):**
```json
{
  "title": "تم إتمام زيارتك بنجاح",
  "body": "نرجو منك تقييم تجربتك ⭐",
  "type": "review_prompt",
  "data": {
    "bookingId": "64a7b2c1f1a2b3c4d5e6f7a1",
    "providerId": "64a7b2c1f1a2b3c4d5e6f7a2",
    "providerType": "Doctor",
    "action": "open_review_screen",
    "status": "completed"
  }
}

```


3. **دور فريق الفلاتر:**
* عند الضغط على الإشعار، يتحقق التطبيق من الـ `action == 'open_review_screen'`.
* يفتح التطبيق شاشة التقييم مباشرة ويمتمر لها الـ `bookingId`، `providerId`, و `providerType`.



---

### الطريقة الثانية: التقييم اليدوي المباشر من ملف الطبيب/الممرض (Manual Profile Review)

1. **ما يحدث في الباك إند:** إذا دخل المريض يدويًا إلى صفحة تفاصيل الطبيب أو الممرض وضغط على زر "تقييم" دون قدومه من إشعار:
* لن يتم إرسال `bookingId`.
* سيقوم السيرفر تلقائياً بالبحث عن **أحدث حجز مكتمل** بين هذا المريض وهذا المزود **ولم يتم تقييمه مسبقاً**، ويربط التقييم الجديد به.




2. **دور فريق الفلاتر:**
* يجمع التطبيق فقط `providerId` و `providerType` والتقييم (`rating` و `comment`) ويرسلها مباشرة للإند بوينت دون الحاجة لتحديد الحجز يدوياً.





---

## 3. تفاصيل الـ API Endpoint الخاصة بالتقييم

* **Endpoint:** `POST /api/reviews`

* **Auth:** Required (`Patient` Token)


* **Request Body ( هيكل الطلب):**
```json
{
  "providerId": "64a7b2c1f1a2b3c4d5e6f7a2",
  "providerType": "Doctor", 
  "rating": 5,
  "comment": "دكتور ممتاز جداً والمعاملة كانت راقية",
  "bookingId": "64a7b2c1f1a2b3c4d5e6f7a1"
}

```


(ملاحظة: حقل `bookingId` اختياري؛ إذا أرسله التطبيق قادماً من الإشعار سيتم اعتماد الحجز المحدد بدقة، وإذا تم إفراغه أو عدم إرساله سيلتقط السيرفر تلقائياً أحدث حجز مكتمل غير مقيم لنفس المزود).
(ملاحظة: حقل `providerType` يقبل حصراً القيمتين: `Doctor` أو `Nurse`).


* **Response النموذجي عند النجاح (201 Created):**
```json
{
  "success": true,
  "message": "Review saved successfully",
  "data": {
    "review": {
      "_id": "64a8c3d2...",
      "patientId": "64a1...",
      "providerId": "64a7b2c1f1a2b3c4d5e6f7a2",
      "providerModel": "Doctor",
      "bookingId": "64a7b2c1f1a2b3c4d5e6f7a1",
      "rating": 5,
      "comment": "دكتور ممتاز جداً والمعاملة كانت راقية",
      "createdAt": "2026-09-15T..."
    },
    "provider": {
      "id": "64a7b2c1f1a2b3c4d5e6f7a2",
      "providerModel": "Doctor",
      "rating": 4.85,
      "totalReviews": 14
    }
  }
}

```

* **سلوك التكرار التلقائي (Idempotency):**
إذا قام التطبيق بإرسال طلب إضافة تقييم مكرر يحمل `bookingId` تم تقييمه مسبقاً في الداتابيز لنفس المستخدم:
بدلاً من إرجاع خطأ `400 Bad Request`، تم جعل الإندبوينت **Idempotent** بحيث ترجع حالة **`200 OK`** مع بيانات التقييم المسجل مسبقاً (`"isExisting": true`)، مما يحمي التطبيق من تعطل الواجهة عند تكرار النقر أو إعادة إرسال الطلب (Network Retry).

---

## 4. إند بوينت استعراض تقييمات مزود الخدمة (Get Reviews)

* **Endpoint:** `GET /api/reviews/:providerId?providerType=Doctor`

* **Query Params:**
* `providerType`: `Doctor` أو `Nurse` (اختياري للفلترة).


* `limit`: أقصى عدد للتقييمات المطلوبة (افتراضياً 100).




* **دور فريق الفلاتر:** استعراض قائمة التقييمات والتعليقات الخاصة بالطبيب أو الممرض داخل بروفايله الشخصي مع صورة المريض واسمه.
